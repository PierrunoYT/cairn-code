# cairn-code — Full Codebase Audit

**Date:** 2026-07-28  **Commit:** `4b5ef46` (main)  **Scope:** all 54 Rust files, 30,199 LOC, `Cargo.toml`/`Cargo.lock`/`deny.toml`/CI
**Method:** full read of every non-TUI module, targeted read of `tui.rs`, plus **executable probes** — every finding marked *Confirmed* was reproduced by running code against the real crate, not inferred from comments.

---

## 1. Executive summary

cairn-code is a from-scratch terminal coding agent with a deliberately tiny dependency surface (8 direct crates, no async runtime, no HTTP client — it shells out to `curl`). The security posture in several subsystems is genuinely above average for a project this size: the filesystem sandbox is capability-based (`cap-std`, `open_dir_nofollow`, symlink-refusing opens) and is backed by real escape tests; `web_fetch` pins the resolved IP with `--resolve` and blocks the full set of RFC special-use ranges; subprocess output is byte-bounded and process trees are killed via job objects / process groups; config writes are atomic with owner-only modes; and print mode (`--print`) fails **closed** on approval-required tools with a dedicated regression test. Branch names in the history (`fix-h01…`, `fix/c03-…`) show prior review rounds landed real hardening.

That makes the three critical findings more surprising, because each one bypasses work that was already done correctly elsewhere in the same codebase:

1. **`cairn-code exec` auto-approves every tool call.** A background thread pumps `"allow"` into the permission channel 20×/second, unconditionally. Every `shell`, `python`, `git`, `file_write`, and MCP call runs unattended with no prompt, no flag, and no config opt-in. This re-opens precisely the hole that was closed for `--print` (the "C-01 regression" test). The subcommand is undocumented in `--help` and `README.md`, and the `--auto` flag that *looks* like it gates this is parsed and discarded.
2. **`shell` and `powershell` panic on any command containing a non-ASCII character.** `echo "café 世界"` aborts the agent thread. Confirmed on this machine.
3. **`json::parse` panics on an out-of-range JSON number.** `{"a":1e999}` kills the process, and this parser is on the path for every provider response, provider *error body*, MCP frame, config file, and tool argument blob.

Below the criticals, the recurring theme is **hand-rolled implementations of solved problems**: a bespoke shell-command rewriter that corrupts unrelated commands, a bespoke secret redactor that is quadratic, a bespoke calendar that computes the wrong date, a bespoke JSON writer duplicated in three files, and four independent copies of the same output-truncation helper — one of which slices by bytes and panics. Notably, `openai_compat.rs` already contains `char_boundary_floor`/`char_boundary_ceil` helpers, so the lesson was learned in one module and not propagated to the other three.

**Testing is a genuine strength in volume (544 tests, 3-OS CI matrix, `cargo-deny`, MSRV job) and a weakness in aim**: every confirmed critical lives in code that has tests around it, but no test exercises the failing input class (non-ASCII, out-of-range numbers, or exec-mode authorization).

**Health score: 58 / 100.** Strong architecture and sandboxing, undermined by three trivially-reachable crashes/bypasses and a layer of unsafe-by-construction string handling.

#### C-1 — `cairn-code exec` auto-approves every tool call
**Category:** Security / authorization **Effort:** S **File:** `src/main.rs:181-186`, `src/main.rs:45-49`

```rust
thread::spawn(move || {
    while !perm_cancel.load(Ordering::Relaxed) {
        let _ = perm_tx.send("allow".to_string());   // <-- unconditional
        thread::sleep(std::time::Duration::from_millis(50));
    }
});
```

`execute_tool_with_policy` is correct — it emits `PermissionRequest` and blocks on `perm_rx`. But in `exec` mode the channel is pre-loaded with an infinite stream of `"allow"`, so **every** approval-gated tool (`shell`, `powershell`, `python`, `git`, `file_write`, `file_edit`, `file_undo`, `web_fetch`, and all MCP tools) executes without a prompt. Only the `deny` list still applies.

Three aggravating factors:
- `--print` mode was explicitly fixed to fail closed here, with the regression test `run_simple_denies_approval_required_tool_by_default` ("C-01 regression"). `exec` reintroduces the same hole through a different door.
- `main.rs:45-49` parses `--auto` and **throws it away** (`"--input-format" | "--output-format" | "--auto" => { i += 1 }`). A user reading the CLI would reasonably conclude auto-approval is opt-in via `--auto`. It is not opt-in at all.
- `exec` appears in neither `print_help()` nor `README.md`. `tests/exec_mode.rs` exercises it but points at an unreachable Ollama host, so no tool ever runs and the bypass is invisible to CI.

**Why it matters:** `cairn-code exec` is the machine-facing entry point — the one most likely to be wired into CI, a git hook, or a webhook. In that position it is a remote-prompt-to-arbitrary-code-execution path with the safety rail wired open.

**Fix:** delete the auto-allow thread. Gate auto-approval behind the `--auto` flag that is already being parsed, and route it through config rather than the channel:

```rust
// main.rs — parse it instead of discarding it
"--auto" => exec_auto_approve = true,

// ...and if set, widen policy explicitly rather than spoofing user consent:
if exec_auto_approve {
    eprintln!("warning: --auto approves every tool call in this run");
    cfg.auto_allow.extend(tool_registry.names());
}
// Without --auto, pass `None` for `interactive` so exec fails closed like --print.
```
Add a test that `exec` without `--auto` refuses a `shell` call.

#### C-2 — `shell`/`powershell` panic on any non-ASCII command *(Confirmed)*
**Category:** Bug / crash **Effort:** S **File:** `src/tools/commit_attribution.rs:313-322` (`is_token_start`), reached from `src/tools/shell.rs:49-53` and `src/tools/powershell_tool.rs:51-52`

`split_next_git_commit` walks the command **byte by byte** (`i += 1`) and hands each index to `match_git_commit_at` → `is_token_start(input, i)`, which does:

```rust
let prev = input[..i].chars().next_back().unwrap_or(' ');   // line 317
```

`input[..i]` slices a `&str` at an arbitrary byte offset. The moment `i` lands inside a multi-byte character, this panics.

Reproduced:
```
echo "café"           -> PANIC  end byte index 18 is not a char boundary; inside 'é'
echo 世界              -> PANIC  end byte index 6 ... inside '世'
grep -r 'naïve' .     -> PANIC  end byte index 12 ... inside 'ï'
echo 🎉                -> PANIC  end byte index 6 ... inside '🎉'
ShellTool.execute("Write-Output \"café 世界\"") -> PANIC
```

**Why it matters:** every `shell` and `powershell` invocation passes through this rewriter first. Any command mentioning an accented filename, a CJK path, a non-English string literal, or an emoji aborts. Because the agent loop runs on a spawned thread (`main.rs:333`), the panic kills that thread while the TUI keeps waiting on `event_rx` — the user sees a permanent hang, not an error. This is a trivially-reached denial of service on ordinary, non-adversarial input.

**Fix (immediate):** iterate characters, not bytes.

```rust
// split_next_git_commit
for (i, _) in input.char_indices() {
    if let Some(start) = match_git_commit_at(input, i) { /* ... */ }
}
```
and make `is_token_start` boundary-safe:
```rust
fn is_token_start(input: &str, i: usize) -> bool {
    if i == 0 { return true; }
    let Some(prev) = input.get(..i).and_then(|s| s.chars().next_back()) else { return false; };
    is_ws(prev) || matches!(prev, ';' | '&' | '|' | '\n' | '(' | ')' | '`' | '"' | '\'')
}
```
See H-1 for why this module should be replaced rather than patched.

#### C-3 — `json::parse` panics on out-of-range JSON numbers *(Confirmed)*
**Category:** Bug / crash, DoS **Effort:** S **File:** `src/json.rs:418`

```rust
serde_json::Value::Number(value) => JsonValue::Number(value.as_f64().unwrap()),
```

With the `arbitrary_precision` feature enabled (`Cargo.toml:18`), `serde_json::Number::as_f64()` returns `None` for any value that parses to a non-finite `f64`. `.unwrap()` then panics.

Reproduced:
```
json::parse(r#"{"a":1e999}"#)                       -> PANIC  called `Option::unwrap()` on a `None` value
json::parse(r#"{"a":-1e999}"#)                      -> PANIC
json::parse(r#"{"error":{"code":1e999,"message":"boom"}}"#) -> PANIC
```

**Why it matters:** `crate::json::parse` is the universal entry point. Reachable from at least:
- every provider streaming event (`anthropic.rs:619`) and non-streaming body (`anthropic.rs:434`),
- **provider error bodies** via `http_client::extract_error_detail:75` — so a hostile or merely buggy endpoint crashes the client by returning `{"error":1e999}`,
- every MCP frame (`mcp/client.rs:369`) — an untrusted third-party server can kill the host process,
- the user and project config files (`config.rs:667`),
- every tool's argument parsing.

**Fix:**
```rust
serde_json::Value::Number(value) => JsonValue::Number(
    value.as_f64().filter(|n| n.is_finite()).unwrap_or(0.0)
),
```
Better still, thread a `Result` through `from_serde_json` and reject the document. Add regression tests for `1e999`, `-1e999`, and `1e-999`. **Note this also silently truncates integers > 2⁵³** (`{"a":123456789012345678901234567890}` parses to an imprecise `f64`) — a separate correctness issue in the same function.

#### H-1 — Commit-trailer rewriter corrupts unrelated commands and shell redirections *(Confirmed)*
**Category:** Bug / correctness, data integrity **Effort:** M **File:** `src/tools/commit_attribution.rs` (whole module)

The module scans raw shell text for `git commit` and splices ` --trailer "Co-Authored-By: …"` at what it believes is the end of the command. It is a substring matcher with no real quoting context, and it gets both halves wrong.

Reproduced (posix dialect, and identically for PowerShell):

| Input | Output |
|---|---|
| `echo "git commit is a command"` | `echo "git commit is a command" --trailer "Co-Authored-By: …"` |
| `grep -r "git commit" .` | `grep -r "git commit" . --trailer "Co-Authored-By: …"` |
| `git commit -m x 2>&1` | `git commit -m x 2> --trailer "Co-Authored-By: …"&1` |
| `git commit -m msg -- src/` | `git commit -m msg -- src/ --trailer "Co-Authored-By: …"` |

End-to-end through the real tool on Windows:
```
ShellTool.execute("Write-Output \"git commit is mentioned here\"")
  -> "git commit is mentioned here\n--trailer\nCo-Authored-By: cairn-code <…>\n(exit code 0)"
```

Three distinct defects:
- **False positives.** `is_token_start` treats `"` and `'` as token starts (line 319), so `git commit` *inside a quoted string* is treated as a real invocation. Any command that merely mentions the phrase — a `grep`, an `echo`, a `sed` script, a log message — gets mutated.
- **Redirection corruption.** `scan_command_end` breaks on `&` but not on `>`/`<`, so `2>&1` splits mid-token. The result redirects stdout to a **file literally named `--trailer`**, backgrounds the command, and runs `1`. That is silent data loss plus altered execution semantics.
- **`--` boundary.** Appending after a `--` pathspec separator turns the trailer into a pathspec; `git` then fails with `pathspec '--trailer' did not match any files`.

Additionally `git commit --amend --no-edit` gains a trailer, mutating a message the user asked not to edit; and `command_already_has_cairn_trailer` is a whole-string check, so any command containing the substring `cairn-code` suppresses injection entirely.

**Why it matters:** this silently rewrites commands the agent and the user asked to run. The `2>&1` case destroys output and creates junk files; the false-positive case breaks working commands for no reason. It is the highest-blast-radius correctness bug in the tree.

**Fix:** stop rewriting shell text. The trailer already works correctly in `git_tool.rs` via structured `args`. Options in order of preference:
1. **Drop the shell/powershell rewriting entirely** and rely on the `git` tool + the `CAIRN.md` instruction to the model.
2. Set the trailer through the environment instead of the command line, which is quoting-agnostic and cannot corrupt anything:
   ```rust
   command.env("GIT_CONFIG_COUNT", "1")
          .env("GIT_CONFIG_KEY_0", "trailer.co-authored-by.ifexists")
          .env("GIT_CONFIG_VALUE_0", "addIfDifferent");
   // or install a prepare-commit-msg hook / commit.template for the session
   ```
3. If text rewriting must stay, tokenize with a real shell lexer, track quote state across the *whole* string (not from the match point), and treat `>`, `<`, `>>`, `2>&1`, heredocs, and `--` as terminators.

#### H-2 — `python` tool panics truncating multibyte output *(Confirmed)*
**Category:** Bug / crash **Effort:** S **File:** `src/tools/python_tool.rs:192-202`

```rust
fn truncate_head_tail(s: &str, max_total: usize, head: usize, tail: usize) -> String {
    if s.len() <= max_total { return s.to_string(); }
    let head_n = head.min(s.len());
    let head_part = &s[..head_n];              // line 198 — byte slice
    let tail_part = &s[s.len() - tail_n..];    // line 199 — byte slice
```

Reproduced:
```
PythonTool.execute(<script printing 40 KB of "é">)
  -> PANIC  end byte index 6000 is not a char boundary; it is inside 'é'
```

Any Python script emitting more than 12,000 bytes containing non-ASCII — a stack trace with a unicode path, `print(json)` of international data, a progress bar with box-drawing characters — crashes the agent thread.

**Why it matters:** identical failure mode to C-2, in a tool the model reaches for constantly. `shell.rs`, `powershell_tool.rs`, and `tools/mod.rs` all implement this same helper **correctly** using `Vec<char>`; only this copy is byte-based (see L-4).

**Fix:** delete this copy and call the shared, char-based `tools::truncate_head_tail`, or reuse the existing `openai_compat::char_boundary_floor`/`char_boundary_ceil` helpers.

#### H-3 — `python` tool deadlocks on large output and reports a false timeout *(Confirmed)*
**Category:** Bug / concurrency **Effort:** M **File:** `src/tools/python_tool.rs:103-125`

The tool spawns with `stdout(piped())`/`stderr(piped())` and then polls `try_wait()` in a sleep loop **without draining the pipes**. Once the child fills the ~64 KB pipe buffer it blocks on `write`, never exits, and the loop kills it at the timeout.

Reproduced:
```
{"code":"import sys; sys.stdout.write('x'*300000)","timeout":8000}
  -> elapsed=8.075s  ok=false  err="python timed out after 8000ms"
```

**Why it matters:** *any* Python producing more than a pipe buffer of output always fails, and fails with a misleading error that tells the model the script was slow rather than chatty. This is the exact bug `powershell_tool.rs:85-98` documents fixing ("Regression test for the deadlock this tool used to hit") and that `process_runner` exists to prevent — the Python tool simply doesn't use either.

Two further gaps in the same block: `child.kill()` (line 113) kills only the direct child, not descendants (no job object / process group, unlike `process_runner`); and `PythonTool` never overrides `execute_with_cancel`, so <kbd>Esc</kbd> cannot interrupt a long run.

**Fix:** route the tool through `process_runner::run`, which already handles concurrent draining, bounded output, process-tree kill, and cancellation:

```rust
let options = RunOptions { timeout: Some(Duration::from_millis(timeout_ms)),
                           head_chars: HEAD_CHARS, tail_chars: TAIL_CHARS };
let result = process_runner::run(cmd, &options, Some(cancel))?;
```

#### H-4 — `redact_secrets` is quadratic *(Confirmed)*
**Category:** Performance / DoS **Effort:** S **File:** `src/redact.rs:36-38`, `:160-161`

`match_secret_at` is called at every byte position and starts with:
```rust
let rest = &bytes[i..];
let s = std::str::from_utf8(rest).ok()?;   // O(n) UTF-8 validation, every position
```
`split_env_assign` then does `s.find('=')` — another full O(n) scan per position.

Measured:

| Input length | Time |
|---|---|
| 50 KB | 56 ms |
| 200 KB | 865 ms |
| 800 KB | **15.16 s** |

4× the length ⇒ ~17× the time. Textbook O(n²).

**Why it matters:** `redact_secrets` runs on provider error text (`http_client::format_status_error:131`) and on every agent LLM error (`agent.rs:253`). `extract_error_detail` caps *plain-text* bodies at 280 chars but returns the **uncapped** string for JSON bodies (`http_client.rs:80`). With `RESPONSE_CAP_BYTES = 8 MiB`, a provider returning `{"error":{"message":"<8 MB>"}}` costs roughly 25 minutes of pegged CPU inside the UI thread's error path.

**Fix:** two one-line changes.
```rust
// redact.rs — validate once, not per position
pub fn redact_secrets(input: &str) -> String {
    // pass `input` (already &str) down; drop the per-position from_utf8
    ... match_secret_at(input, i) ...
}
fn match_secret_at(s_full: &str, i: usize) -> Option<usize> {
    let s = s_full.get(i..)?;   // O(1)
    ...
}
// and bound the scan in split_env_assign:
let eq = s.get(..MAX_ENV_NAME_LEN).unwrap_or(s).find('=')?;
```
Also cap `extract_error_detail`'s JSON branch at 280 chars like the plain-text branch.

#### H-5 — Commit rewriter is quadratic in the worst case *(Confirmed)*
**Category:** Performance **Effort:** S **File:** `src/tools/commit_attribution.rs:142-165`

`match_git_token` calls `s.to_ascii_lowercase()` on the **entire remaining string** at every candidate token start.

Measured (whitespace-heavy command, i.e. every position is a token start):

| Tokens | Command length | Time |
|---|---|---|
| 1,000 | 2 KB | 1.4 ms |
| 4,000 | 8 KB | 16.3 ms |
| 16,000 | 32 KB | 247 ms |
| 64,000 | 128 KB | **3.95 s** |

**Why it matters:** a 128 KB generated command (a long `sed`/`awk` program, an inlined script, a big `find … -exec` chain) burns four seconds of CPU *before the command starts*. It also allocates ~n²/2 bytes.

**Fix:** lowercase only the first token:
```rust
fn match_git_token(s: &str) -> Option<usize> {
    let token_end = s.char_indices()
        .find(|(_, c)| is_ws(*c) || is_shell_meta(*c))
        .map_or(s.len(), |(idx, _)| idx);
    if token_end == 0 { return None; }
    let base = s[..token_end].rsplit(['/', '\\']).next().unwrap_or("");
    let base = base.strip_suffix(".exe").or(base.strip_suffix(".EXE")).unwrap_or(base);
    base.eq_ignore_ascii_case("git").then_some(token_end)
}
```
Subsumed if H-1 is fixed by deleting the module.

#### H-6 — Cancelling mid-tool-loop corrupts conversation history
**Category:** Bug / correctness **Effort:** M **File:** `src/agent.rs:375-405`

```rust
for tu in &tool_uses {
    if cancel.load(Ordering::Relaxed) {
        return Ok(());          // <-- returns with results pushed for SOME tools only
    }
    ...
    self.messages.push(/* ToolResult */);
}
```

When the model emits several tool calls in one turn and the user presses <kbd>Esc</kbd> after the first completes, the loop returns having appended a `ToolResult` for tool 1 but none for tools 2..n — while the corresponding `ToolUse` messages were already pushed at line 365-367.

**Why it matters:** the next request contains `tool_use` blocks with no matching `tool_result`. Anthropic rejects this outright (`tool_use ids must have corresponding tool_result blocks`), and OpenAI-compatible endpoints behave similarly. The session is then permanently unusable until `/clear` — and it has already been checkpointed to disk in that state (line 404), so `--resume` reloads the broken transcript.

**Fix:** on cancellation, synthesize a result for every outstanding call before returning.
```rust
for tu in &tool_uses {
    let result_str = if cancel.load(Ordering::Relaxed) {
        "Error: cancelled by user before this tool ran".to_string()
    } else { /* normal execution */ };
    self.messages.push(/* ToolResult { tool_use_id: tu.id, content: result_str } */);
}
```
Add a test that cancels between two tool calls and asserts `tool_use` count == `tool_result` count.

#### H-7 — `file_read` returns unbounded content into the model context *(Confirmed)*
**Category:** Performance / cost / DoS **Effort:** S **File:** `src/tools/file_read.rs:54-113`

There is no cap on total output. Every other read path in the tree is bounded (`grep` 1 MiB, `memory` 1 MiB, `shell` 12,000 chars, `web_fetch` 10,000 chars, MCP 16 MiB), but `file_read` without an explicit `limit` returns the whole file.

Reproduced: a 4 MB file returned **4,128,953 bytes** in a single tool result.

**Why it matters:** ~1 M tokens in one tool result. Either the request is rejected for exceeding the context window (after paying to build it) or it costs real money and evicts the rest of the conversation. `read_to_string`-style buffering also means a large file is materialised in RAM. `needs_permission()` is `false`, so nothing gates it.

Secondary: line 94 does `format!("{line_number}:{line}\n")` per line — one allocation per line; use `write!` into the output buffer.

**Fix:** add a byte/char budget mirroring `grep`'s, and report truncation:
```rust
const MAX_READ_BYTES: usize = 256 * 1024;
// stop when result.len() >= MAX_READ_BYTES, and append
// "\n… [truncated at 256 KiB; pass offset/limit to read more]"
```

#### H-8 — "Always allow" is global, permanent, and command-agnostic
**Category:** Security / authorization design **Effort:** M **File:** `src/agent.rs:499-506`, `src/config.rs:441-484`

```rust
PermissionDecision::AlwaysAllow => {
    if !always_allowed { self.config.auto_allow.push(permission_key); }
    let _ = crate::config::save_permissions(&self.config);
```

`permission_key` for `ShellTool` is just `"shell"` (the trait default, `registry.rs:11-13`). So a single "always allow" on one `rm -rf ./build` grants **every future shell command, in every project, forever**, persisted to the user-global `~/.config/cairn-code/config.json`.

**Why it matters:** this is the primary consent mechanism for the most dangerous tool in the product, and it has no granularity in either dimension — no command scoping and no workspace scoping. `memory` shows the intended pattern (`permission_key` → `"memory:save"`), so the machinery exists; `shell`/`powershell`/`python`/`git` just don't use it.

Related defect: the three policy checks read **different keys** — `needs_ask` uses `tu.name`, `always_allowed` uses `permission_key`, `denied` uses `tu.name` (`agent.rs:452-457`). Consequences: `auto_allow: ["memory"]` does *not* auto-allow `memory:save`, and `deny: ["memory:save"]` does *not* deny it. See M-20.

**Fix:**
- Give the exec tools a meaningful `permission_key` (e.g. `shell:<argv0>` → `shell:git`, `shell:cargo`) so consent is per-program.
- Scope `auto_allow` per workspace: store `{"auto_allow_by_workspace": {"/abs/path": [...]}}` rather than one global list.
- Make `denied` consult both `tu.name` and `permission_key`.
- Offer "allow for this session" as the default affordance, persisting only on explicit request.

#### H-9 — `file_edit` silently replaces the first of several matches *(Confirmed)*
**Category:** Bug / data integrity **Effort:** S **File:** `src/tools/file_edit.rs:66-79`

With `replace_all: false` (the default) and multiple occurrences, the tool replaces occurrence #1 and reports success.

Reproduced: file `"a a a"`, edit `old_string:"a" → "B"` ⇒ `Ok("Applied 1 edit(s)")`, content `"B a a"`.

**Why it matters:** the model believes it made a uniquely-identified, surgical edit. When `old_string` is ambiguous the change lands somewhere arbitrary — commonly the wrong function, the wrong branch, or an import instead of a usage. Claude Code and every mature edit tool treat non-uniqueness as an **error** for exactly this reason. Silent wrong-location edits are hard to notice and land in commits.

**Fix:**
```rust
let count = content.matches(old_string).count();
if !replace_all && count > 1 {
    return Err(format!(
        "old_string appears {count} times in {file_path}; \
         include more surrounding context to make it unique, or pass replace_all:true"
    ));
}
if old_string.is_empty() {
    return Err("old_string must not be empty".into());   // see M-2
}
```

#### H-10 — Timeout kills only the direct child in `python`/`powershell`, and the drain-join can hang
**Category:** Concurrency / resource leak **Effort:** M **Files:** `src/tools/python_tool.rs:113-114`, `src/tools/powershell_tool.rs:105-108`

Both tools spawn directly rather than through `process_runner::ManagedChild`, so neither gets a job object (Windows) or process group (Unix). `child.kill()` reaps the shell/interpreter and leaves descendants running.

`powershell_tool` compounds it: after killing the child it calls `stdout_handle.join()` / `stderr_handle.join()` (lines 107-108). Those threads are blocked reading pipes that a **surviving grandchild** still holds open, so the join never returns — the tool hangs forever instead of timing out. `shell.rs` avoids this precisely because `process_runner` kills the whole tree first (and has `test_timeout_kills_descendants` to prove it).

**Fix:** move both tools onto `process_runner::run`, which already solves group kill, bounded drain, and cancellation. This also fixes H-3 and gives both tools <kbd>Esc</kbd> support.

#### M-17 — Environment mutation races with reader threads
**Category:** Concurrency / undefined behaviour **Effort:** M

## 4. Category summaries

**Bugs.** Three confirmed panics (C-2, C-3, H-2), one confirmed deadlock (H-3), one confirmed silent data-integrity failure (M-1), and a conversation-corrupting cancellation path (H-6). The unifying cause is byte-oriented string handling in code that receives arbitrary text.

**Security.** The sandbox, SSRF defence, and secret-at-rest handling are well built and well tested. The failures are at the edges: an entry point that bypasses consent entirely (C-1), consent that is too coarse to be meaningful once granted (H-8), lists that key off different identifiers (M-20), one network tool hardened and its sibling not (M-21), and untrusted MCP content entering the context unbounded (M-22).

**Performance.** Two confirmed quadratic algorithms on attacker- or model-influenced input (H-4, H-5), one unbounded context injection (H-7), a network call on the per-turn hot path (M-13), a full input copy on every JSON parse (M-30), and repeated subprocess probes (L-6). Prompt caching is instrumented but never enabled (M-11).

**Architecture.** The `Provider`/`Tool` trait boundaries are clean and the layering is sensible. The debt is horizontal: four truncation helpers, three JSON writers, two output collectors, and two subprocess-management strategies (`process_runner` vs. direct `spawn`) — with the bugs concentrated in the copies that didn't get the fix. `Message`-per-content-block forces provider adapters to reassemble multi-block turns. Credentials travel through the process environment, which is what makes M-17 possible.

**Code quality.** 230 lines of dead parser (M-30), duplicated helpers (L-4), dead underscore-prefixed API (L-5), a literal duplicated statement (L-1), and 39 unenforced Clippy warnings (L-12).

**Concurrency.** `std::thread::scope` usage in `http_client` and `process_runner` is careful and correct. The problems are environment mutation racing with readers (M-17), a thread-local that assumes single-threadedness (M-26), unlocked config read-modify-write (M-18), a join that can hang on surviving grandchildren (H-10), and a poll loop that may never terminate (M-16).

**Error handling.** `RunError`/`RequestError`/`ByteLimitedRunError` are well-designed and the user-facing messages in `format_transport_error`/`format_status_error` are genuinely helpful. Against that: silent `unwrap_or_default()` on the system prompt (M-24), `compact_history` returning `0` on failure (M-23), `receive_output` converting a panicked drain thread into empty output (`process_runner.rs:348`), `create_parent_dirs` reporting every failure as "outside the workspace" (`workspace.rs:70-77`), and exec reporting success on error (M-8).

**Testing.** 544 tests, a 3-OS matrix, `cargo-deny`, and an MSRV job — well above average. But every confirmed critical sits in tested code whose tests don't cover the failing input class. Recommended additions: property/fuzz tests for `json::parse`, `commit_attribution`, and `redact_secrets`; non-ASCII inputs for every tool; an exec-mode authorization test; a cancel-mid-tool-loop history-integrity test; and a `#![forbid]`-style lint or test asserting no `&str[..n]` on externally-sourced strings. Six files have no tests (`main.rs`, `mcp/tools.rs`, `file_history.rs`, `provider.rs`, `lib.rs`, `llm/mod.rs`) — `main.rs` is where C-1 lives.

**Dependencies.** Commendably lean at the top (8 direct), 308 transitive. Two permanently-ignored advisories (L-18), one duplicated crate version (L-19). Licences are constrained by an explicit allowlist in `deny.toml` — good practice. No unmaintained *direct* dependency.

**Documentation.** `CAIRN.md` and the module-level doc comments are unusually thorough. Two gaps: the `exec` subcommand is undocumented (L-15), and several comments assert invariants the code doesn't guarantee (L-20).

**API & interfaces.** The stream-json `exec` protocol has a mislabelled field (M-7) and a wrong exit status (M-8) — both breaking for any consumer. `grep`'s `include` silently rejects the obvious syntax (M-4). Tool schemas largely lack `description` fields, which is the cheapest available accuracy win for tool-calling.
